## Fix 16 — correct native mesh delivery and SOS encoding (NSVC-1 + NSVC-5, both Major)

Fixes NSVC-1 (report line 1500) and NSVC-5 (report line 1505), both in the native mesh path.

NSVC-1: locally queued plaintext is encrypted separately for each connected peer (send loop), but a receiving peer B stored the received ciphertext/signature as a relay with `needsEncryption` left false and re-emitted that ciphertext verbatim to C. C holds a different private key, so decrypt returns null and the frame is skipped — A→B→C could never deliver A's report text to C, even though B decrypted it successfully. Hop allowance only moved bytes addressed to B.

NSVC-5: `AppRepository.broadcastMeshIntel` selected wire type `echo` for kind `sos`, and `sendSos` uses that path before HTTP. MeshService encrypts EVERY locally queued type with AES-GCM, including echo — but MeshInbound treats echo as plaintext base64 and bypasses decryption, so `notifyListeners` received raw ciphertext decoded as UTF-8 ("encrypted garbage"). AppRepository could not parse that as JSON intel and never admitted the SOS coordinates. This contradicted MeshInbound's comment that no legitimate caller emits echo.

### The fix

NSVC-1 — re-encrypt on relay (`MeshService.kt`, `MeshQueue.kt`):
- `MeshQueue` (companion) gained a pure, JVM-tested relay policy: `RelayMode { VERBATIM, REENCRYPT, NONE }` + `relayMode(type, decrypted, hopsLeft)`. `hopsLeft <= 0` → NONE; `echo` → VERBATIM (plaintext by design, every hop reads it); a decrypted non-echo frame → REENCRYPT; an undecryptable frame → VERBATIM (the intended recipient may be downstream).
- `handleIncomingMessage` now dispatches on that policy instead of always relaying verbatim, still BEFORE the listener notify (audit B1 order preserved) and still under the same queue bound. The verbatim construction moved verbatim into `enqueueVerbatimRelay`.
- `enqueueReencryptedRelay(payload, plaintext)` mirrors `broadcastMessage` exactly: one snapshot for the PoW prefix, the origin identity and the eventual encryption; a fresh PoW solved for (origin messageId, our snapshot id) (difficulty 8, cheap); the same type and coordinates; `hopCount = 0`; one hop consumed (`hopsLeft - 1`); `needsEncryption = true` with the snapshot attached, so the send loop encrypts it separately for each of our peers. The re-encrypted copy is a fresh origin frame under our own key — the origin's signature does not (and cannot) survive a re-encryption, because the ciphertext it covers is replaced. **The copy keeps the origin `messageId`**: both mesh dedup mechanisms (anti-replay seen-cache, Trickle/forwarded-marker suppression) are keyed by it, so a fresh id would make every copy look like a new message and fan out exponentially (~66k frames for one report in a 10-device clique at MAX_HOPS 5). With the origin id, the markers bound re-sends per peer; the nonce stays fresh, so the copy still passes the seen-cache at its first hop.
- Fallbacks preserve today's behavior exactly: an oversized plaintext (> 256 KB, which `broadcastMessage` would reject at queue time) falls back to the verbatim relay; a PoW-budget exhaustion or any exception while building the copy falls back to the verbatim relay. Exactly one copy is admitted per frame — never both.
- Scope note: the re-encrypted copy's frame timestamp is set at send time by `encryptForPeerWithSnapshot` (like every local message), so content can keep gossiping hop by hop while it keeps moving; the hop budget (`MAX_HOPS`), not the clock, bounds its spread. The verbatim relay keeps the origin timestamp. A frame whose bytes are not valid UTF-8 re-queues with the same replacement characters the UI path already produces.
- Follow-up (not this part): the same report can still be NOTIFIED twice when heard over two paths — the seen-cache key covers (messageId, nonce) and the re-encrypted copy's nonce is fresh, so the second copy is accepted and displayed again. Content dedup in `onMeshPlaintext` (skip notify/re-origination for a (type, plaintext, lat, lng) already seen within a window) is a separate change; the wire fan-out is bounded by the kept messageId, but the duplicate display is not fixed here.

NSVC-5 — SOS rides as `report` (`AppRepository.kt`):
- `broadcastMeshIntel` now always sends `"report"` instead of `"echo"` for kind `sos`. SOS is JSON intel like any report: receivers decrypt it through the normal path, `onMeshPlaintext` parses the JSON, and the coordinates are admitted to `meshIntel`. No legitimate caller emits echo anymore; the wire type stays accepted on the receive path for backward compatibility with older builds. SOS stays E2EE (its coordinates are sensitive emergency data) — the alternative of sending echo as true plaintext would have exposed them to any nearby sniffer.

## Fix 17 — preserve native snapshots across failed, empty and oversized refreshes (NREP-1 + NREP-2 + NREP-3 + NAPI-1, all Major)

Fixes NREP-1, NREP-2, NREP-3 (report lines 1352–1354, all in `AppRepository.kt`) and NAPI-1 (report line 1543, in `ObservatoryApi.kt`). The four compose: NAPI-1 *manufactures* malformed-success bodies (truncation), NREP-2 *fails to recognise* them (empty list instead of failure), NREP-1 *stamps and persists* a partial/mixed refresh as a full success, and NREP-3 *resurrects* the stale snapshot the other three failed to replace. All four land together — any one alone leaves a hole.

NREP-1: `refreshAll` decided "everything worked" with `||` (OR) over reference-inequality tests, so one endpoint succeeding stamped the whole refresh as successful, advanced `lastSyncMs`, and persisted a snapshot mixing fresh data for one list with stale data for the other three — contradicting the function's own kdoc promise ("only a fully-successful pass updates lastSyncMs/persist"). NREP-2: the parsers collapse "malformed body" and "genuinely empty array" into the same `emptyList()`, and `fetchList` returned that list for every HTTP 200, so a malformed 200 (`{}`) wiped last-good data instead of preserving it. NREP-3: `persistSnapshot` returned early whenever reports AND hotspots were both empty, even after an entirely successful refresh established that both are empty — the old snapshot was never replaced or cleared, so the next cold start restored removed/resolved threats (and stale safezones); a safezones-only snapshot was never persisted at all. NAPI-1: `readBody` allocated `MAX_RESPONSE_BYTES + 1` (the `+1` sentinel byte exists precisely to detect overflow) and then never checked it — it decoded only the first 32 KB and handed the truncated prefix back as a successful `Result.Ok`. The server serves full reports/satellite lists with no size ceiling, so any busy period legitimately exceeds 32 KB; truncated JSON fails to parse as an array, so the parsers returned `emptyList()` and (via NREP-2) the app wiped its last-good data.

### The fix

NREP-1 — AND, not OR (`AppRepository.kt`, `RefreshPolicy.kt`): `refreshAll` now keeps the nullable fetch results separate from the `?: prev` fallback and decides success with `RefreshPolicy.refreshSucceeded` (all four non-null). Partial refreshes still *display* the fresh data that did arrive (last-good-correct); only `lastSyncMs` advancing and `persistSnapshot()` are now gated on all four succeeding. The old `!==` identity trick is deleted. The kdoc at ~458 already promised this behaviour and needed no change.

NREP-2 — malformed 200 is a failure (`AppRepository.kt`, `RefreshPolicy.kt`): `fetchList` now checks an empty parse result against `RefreshPolicy.isGenuineEmptyBody` — true only for a body that is exactly `[]` modulo whitespace. Any other body that parses to nothing returns `null` (failure → caller keeps last-good data). A valid array whose every item is malformed is also treated as a failure (zero usable items must not wipe last-good data) — documented as intentional in the code. `Models.kt` is untouched (its full review is pending, and the finding says so). `restoreSnapshot` needs no change: its inputs are always valid arrays (`"[]"` or a real stored array string).

NREP-3 — persist the empty snapshot (`AppRepository.kt`): the early return in `persistSnapshot` is deleted — that is the whole fix. After a fully-successful refresh that establishes zero threats, the written snapshot is `{reports: [], hotspots: [], safezones: […], lastSyncMs: <fresh>}`, replacing the stale record; the safezones-only case is fixed by the same deletion. The other four callers (submit/drain paths) now also write when the lists are empty — harmless, they write the current state (empty arrays + current `lastSyncMs`, possibly 0 on a never-synced device), and `restoreSnapshot` already defaults missing keys to `"[]"` / `0L`. Deleting the stored key instead was considered and rejected: persist-empty keeps `lastSyncMs` and the safezones in one code path.

NAPI-1 — detect overflow, fail loudly, raise the cap (`ObservatoryApi.kt`): `readBody` now returns `String?` — `null` when a 2xx body could not be read completely (overflow or stream error) — and `request` maps that to `Result.TransportFailure` (callers already treat that as "keep last-good / queue and retry"). The bounded read is extracted as the pure, JVM-tested `readBoundedBody(stream, maxBytes)` (`null` = overflow or stream error; a body of exactly `maxBytes` decodes fully; a truncated body is never decoded, so a multi-byte character can never be split). Error bodies keep the pre-Fix-17 behaviour (`readErrorBody`: truncated at the cap, `""` on failure) — the status itself was read successfully, and turning an unreadable error body into a transport failure would flip a known 4xx into the retryable path. `MAX_RESPONSE_BYTES`: `32 * 1024` → `1 * 1024 * 1024` (now `internal` so the test pins it); the class kdoc's false "bounded 32KB reads — every endpoint returns bounded JSON" claim is corrected to the real contract (bounded at 1 MiB, anything larger is a transport failure, never a truncated success). The 1 MiB cap is still a cap — a catastrophic fire season could in principle push a list past it; the outcome is then fail-loud (last-good preserved, retry next poll), never silent corruption. `TeamLocationService.kt` has its own separate 4 KB `readBody` — out of scope for this part, untouched.

## Fix 18 — make native emergency queues durable before confirming submission (NREP-4 + NREP-5, both Major)

Fixes NREP-4 and NREP-5 (report lines 1355–1356, both in `AppRepository.kt`). NREP-4: `persistQueues` took a snapshot and then passed it to an unsynchronized writer, so two writers for the same kind could install their files in the opposite order to the order their snapshots were taken — the older snapshot won the disk, silently losing the newer entries from disk while they remained in memory (visible only after process death, when the restore reads the stale file). All writers also shared one tmp filename per kind (`queue_<kind>.json.tmp`), so concurrent writers could interleave bytes into the same tmp file and rename a torn file into place. NREP-5: `persistQueueFile` stopped serializing when cumulative payload length exceeded 12,000,000 chars, so legal ~700,000-char SOS audio payloads exhausted the budget after ~17 entries — below the queue capacity of 60 — and the newer accepted entries stayed memory-only (only `Log.w` reported it) while `sendSos` still called `onDone(true, …, OFFLINE_QUEUED_MSG)` promising storage and automatic sending. Process death lost those omitted requests. Disk write failures were similarly swallowed without changing the callback outcome.

### The fix

NREP-4 — serialize snapshot + write as one atomic step (`AppRepository.kt`): one lock per queue kind (`reportQueuePersistLock`, `sosQueuePersistLock`); `persistQueues` now takes the snapshot AND writes the file inside the same per-kind lock (`persistQueueFileLocked`), so two writers for one kind are totally ordered — the later snapshot is always the later install. The lock also fixes the shared-tmp interference (same-kind writers can no longer interleave in the tmp file); unique tmp names were considered and rejected — they leave the stale-overwrite race intact, and are unnecessary once the lock is held. The `renameTo` fallback is fixed in the same function: if the rename fails, it is retried once and, if it still fails, the old file stays intact and the persist reports failure — the old direct `f.writeText(...)` fallback (a crash mid-write would corrupt the queue) is deleted. Lock-ordering discipline is documented in the code: the persist lock is the OUTER lock, the queue monitor is taken only inside it via `snapshot()`; no code path calls `persistQueues()` while holding a queue monitor (verified: `enqueue`/`commit`/`reserveDue` never call persist; the drain loop commits — releasing the monitor — before persisting).

NREP-5 — honest budget + conditional confirmation (`AppRepository.kt`, `OfflineQueue.kt`): (1) `MAX_PERSIST_TOTAL_CHARS` raised 12,000,000 → 48,000,000 (60 entries × ~700,000 chars ≈ 42 M, rounded up with headroom for JSON escaping; the derivation is in the code comment). Worst case two files × ~48 MB (+ one tmp each during write) is the honest price of the "durable queue" promise. `MAX_PERSIST_ENTRY_CHARS` (800,000) is unchanged — a legal max SOS audio (~700 k) fits; it only rejects runaway garbage. A report with a near-max photo (500 k-char data URI — the builder cap in ApiPayloads) still fits under it. (2) `persistQueueFile` now returns a `QueuePersistResult` (persisted / omitted / failed; `durable` is true only when every entry in the snapshot is on disk) instead of swallowing failures in `Log.w`. The budget/omission selection is extracted into the pure, JVM-tested `OfflineQueue.selectPersistable` (oldest first; oversized entries skipped; once the budget is exceeded, that entry and every newer one is omitted; an entry exactly at the boundary persists). The two offline branches persist FIRST and confirm only on durable: `submitReport` calls `onDone(true, OFFLINE_QUEUED_MSG)` only when the reports persist is durable, else `onDone(false, QUEUE_PERSIST_FAILED_MSG)` ("تعذر حفظ الطلب على الجهاز — سيُحاول إرساله طالما التطبيق مفتوح"); `sendSos` likewise, and does NOT set `queuedWhileOffline = true` on the failure path (that flag is cleared by the drain loop only when the queue empties, and it would keep promising a send that process death will cancel). In both cases the entry stays in memory — the drain loop can still send it while the app lives (best effort). The drain loop now logs an incomplete persist (omitted/failed counts per kind) and keeps running — a persist failure must never kill the 20 s loop, and `persistQueues()` never throws (the `runCatching` no-throw property is preserved). `persistSnapshot()` failures stay out of scope (Fix 17 owns that function); the dispatcher is left alone (`Dispatchers.Default`, per the prep recommendation); `OfflineQueue`, `readQueueFile`/`restoreQueues` (no format change, no migration), and the mesh broadcast calls are untouched.
